# V6.2 conversational assistant

The assistant is enabled by `TEXT2SQL_CONVERSATIONAL_AGENT_ENABLED=true` in
`.env.example`. Set the flag to `false`
for the legacy path. Its client-facing prose is
generated by the selected assistant provider/model, except when that provider fails:
then the API returns an explicitly marked assistant-service failure. The assistant
never executes model-authored SQL directly.

```text
Client message
  -> load same-database accepted conversation/result
  -> top-layer LLM decides intent and action for every turn
  -> LangGraph reason -> typed tool input -> authorized tool when facts are needed
       -> compact observation -> reason again (maximum three tool steps)
  -> top-layer LLM answer or clarification
  -> existing history and presentation response contract

ask_data -> existing Text-to-SQL chat service
          -> retrieval -> grounding -> SQL model -> SQLGlot/read-only execution
          -> conditional recovery
```

The `ToolName` allowlist and typed input/observation models in
`conversational_agent.py` constrain tool calls. Metadata tools inspect the configured
database and approved profiles/glossary. `ask_data` delegates to the existing
governed SQL path. Investigation objectives use isolated, bounded sessions so
intermediate breakdown queries do not replace the client's accepted SQL.
`analyze_result` performs descriptive statistics, returned-row rankings and,
for complete unambiguous time series, first-to-last absolute/percentage change. It does **not** infer
causality. Chart operations use the existing result-reusability gate and
validated chart planner. The assistant's final response sees at most ten data
rows plus row count, completeness and chart metadata; the UI retains the
underlying executed result separately.

The assistant and delegated SQL path use one request-local `RequestBudget` via
a context variable. This covers top-layer, SQL-generation and database calls
that already claim the core budget. Default limits are 180 seconds, eight model
calls and 24 database calls; configure `TEXT2SQL_ASSISTANT_*` to change them.
The response ledger includes the assistant calls alongside downstream calls.

The existing `ConversationState`, in-memory accepted-result cache, and
`RunHistoryStore` remain the authoritative memory. Previous state is ignored
after a database switch. The client-facing final answer and its chart are saved
once, after the top model finishes; delegated investigation runs remain separate.
Failed tool actions do not overwrite the accepted SQL. The initial routing
prompt receives only the presence of accepted SQL; full accepted SQL and its
referenced tables/columns are returned by `explain_existing_result` on demand.
Presenting an accepted result reads its bounded in-memory snapshot rather than
executing SQL again. If the top model fails while writing the final answer
after a governed query, the existing query response is returned with an
`assistant_response_unavailable` provenance marker; an initial routing failure
still fails closed. Correction, optimization, correctness review and reset are
distinct top-model intents that delegate to the existing conversation service.
No new database migration is required.

## Verified behavior

- Greeting: one assistant decision/answer call, no tool or SQL call.
- Schema/glossary lookup: a top-model decision, one metadata action and a top-model answer.
- New analytical query: one assistant tool-selection call, existing governed SQL
  generation, then one assistant response call.
- Compatible chart follow-up: top-model decision, existing cached result and chart gate,
  then top-model answer; no new SQL-generation call (integration-tested).
- Investigation: distinct bounded governed analytical objectives; descriptive
  calculations only; model may stop after sufficient observations.

These are measured **call counts in mocked integration tests**, not live provider
latency, token or answer-accuracy benchmarks. The repeatable local
`benchmarks/benchmark_assistant.py` measured 30 repetitions on this checkout:

| Synthetic case | Median orchestration time | Mock model calls | Mock SQL handler calls | Mock tokens |
|---|---:|---:|---:|---:|
| Greeting | 7.017 ms | 1 | 0 | 15 |
| New query | 7.627 ms | 2 | 1 | 30 |

This excludes provider and database latency, and mock token counts do not
predict paid token usage. No matched before/after live-provider latency run was
available; no latency improvement is claimed. Run `pytest`, `ruff` and `mypy`
as listed in the README for local verification.

## Remaining limits

- The model may still request an unhelpful investigation breakdown; real-business
  accuracy and causal reasoning require a frozen evaluation set with ground truth.
- The accepted conversation contract is persisted, but a dedicated durable,
  versioned investigation summary and multi-user authorization are not present.
- The analytical tool covers descriptive statistics and simple complete-series
  changes; contribution/decomposition calculations need explicit additive metric
  lineage before they can be trusted.
- Provider errors and budget exhaustion are explicit service failures, not
  model-generated answers. A shared deployment also needs tenant authorization
  and an end-to-end live-provider load/latency evaluation.
